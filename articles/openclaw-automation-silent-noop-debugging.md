自分で運用している学習用サイトが「動かなくなったかも」と言われたとき、実際には障害なのか、仕様なのか、環境側の問題なのかを切り分けるのは意外と難しい。今回は、自身で運用しているpwn学習サイト TofuCTF（GitHub Pages + Cloudflare Workers）について「動いていない」という報告を受けた日の調査を、AIアシスタントに委任して読み取り専用で実施した記録をまとめる。結論として、サイトの全面障害は再現しなかったが、その過程で「正常終了の履歴が本当に正常を意味しない」ケースや、UAによる403の罠など、再利用可能な切り分けの型が得られた。

## 背景

TofuCTFは、GitHub Pagesで公開する静的サイトと、進捗同期用のCloudflare Workers（D1使用）、そして各問題をローカルDockerで動かす配布tarで構成している。毎日1問ずつpwn問題を追加する日次ジョブが動いており、2026-10-16に「Wraparound Waffle #30」が公開されていた。

10月19日、「TofuCTFが動作していないのでは」という報告があり、まず原因の想定を置かずに、現状の確認だけを行うことにした。利用しているAIアシスタント（OpenClaw）のセッションで、読み取り専用の診断タスクをサブエージェントとして切り出し、ファイル変更や設定変更なしで調査させた。

## 切り分けで実際に確認したこと

診断は、サイト本体 → Worker → 日次ジョブの履歴 → ホスト環境の順に進めた。

### 1. サイト本体と配布ファイルの整合性

公開URLから`index.html`、`app.js`、`auth.js`、`challenges.json`、CSSを取得し、ローカルリポジトリのファイルとバイト一致を比較した。さらに`challenges.json`に記載された30問すべての配布tarを取得し、SHA-256でローカルと一致すること、tarとして正常に展開できることを確認した。

結果はすべてHTTP 200・一致・正常だった。つまり、静的ファイルの配信も配布アーカイブも壊れていなかった。

### 2. Workerの挙動とUAによる403

進捗同期用のCloudflare Workerに対して、`/health`と未認証の`/auth/session`、`/api/progress`へGETを送った。ここで興味深い違いがあった。

- ブラウザ相当の`User-Agent`（`Mozilla/5.0`始まり）では、`/health`が200、未認証エンドポイントは意図通りの401、CORSヘッダも正しい。
- Python `urllib`のデフォルトUA（`Python-urllib/3.x`）では403になる。

```text
User-Agent: Mozilla/5.0 ...  → /health 200、未認証APIは401（正常）
User-Agent: Python-urllib/3.x → 403
```

Cloudflareのボット対策に由来するとみられる挙動で、Worker側のコードにUA判定のロジックは書いていない。スクリプトで疎通確認するとき、「Python標準ライブラリのUAで403が返る＝障害」と誤認しないよう、必ずブラウザ相当のUAを併用して比較するのが安全だと分かった。実装した診断スクリプトは、複数のUAで同じエンドポイントを叩いて結果を並べて表示するようにした。

### 3. 「正常終了」が健康を意味しないケース

日次の問題追加ジョブの実行履歴を見ると、10月17日〜19日も「正常終了」していた。しかし`challenges.json`の最新は10月16日のままで、実際には新しい問題が追加されていなかった。

原因は、ジョブの指示に「問題数が30以上ならSeason 01完走として追加しない」という停止条件が書かれていたことだ。つまり、この挙動は仕様どおりで、ジョブは毎日正しく起動し、正しく「追加しない」を選択して終了していた。

監視の観点では、「ジョブが正常終了しているか」だけを見ていても、実データが更新されているかは別問題だと再確認させられた。今回は利用者自身が「最新問題が古い」と気づいたことで発覚したが、稼働継続を確認する仕組みを作るなら、ジョブの終了コードではなく成果物（この場合は`challenges.json`の最終更新日）を監視するべきだった。

### 4. 診断環境そのものの問題

調べていくと、この診断を実行しているホスト側に、サイトとは無関係な問題が2つ見つかった。

- ディスク使用率が100%で、空きが約59MBしかない。
- Dockerサービス自体は起動しているが、実行ユーザーに`/var/run/docker.sock`の権限がなく、コンテナの起動検証ができない。

これらはローカルでの問題起動や今後の検証には支障するが、GitHub Pagesの閲覧障害の根拠にはならない。「調査側の環境が壊れている」ことと「調査対象が壊れている」ことを混同しないために、診断結果を報告するときはこの区別を明示したほうがよい。

## 対応

サイト側は障害として再現しなかったため、復旧作業は発生しなかった。報告者（自分）に、症状がページ表示・ログイン同期・ローカル起動・問題更新のどれを指すのかを確認する質問を返した。

その後、報告の意図が「10月19日なのに最新問題が10月16日のまま」という点だと判明したため、30問上限の停止条件を「上限を設けず毎日1問を継続」するようジョブの指示文だけを修正した。このとき、ジョブのスケジュール・モデル・配信先など他の設定項目が一切変わっていないことを、変更前後の設定を比較して確認してから適用した。

## 学び

- **「正常終了」の履歴を鵜呑みにしない。** 停止条件が明示的なno-opとして設計されていると、ジョブは毎日成功したまま何も生産しない。稼働確認はジョブの終了状態ではなく、成果物の実データで行う。
- **UAで応答が変わる可能性を前提にする。** Cloudflareなどのエッジはスクリプトの既定UAをブロックすることがある。疎通確認は最低2種類のUAで行い、403を即「障害」と判断しない。
- **診断環境と調査対象を混同しない。** ディスク_fullやソケット権限の不足は調査側の制約であり、対象サイトの障害とは別の事象として扱う。
- **原因の想定を先に置かない。** 「動かない」が何を指すのか（表示、認証、起動、更新）は、本人にしか分からない。再現しない場合は一通りの健全性を確認したうえで、症状を1つに絞る質問を返すのが最短だった。

なお、ブラウザでの実描画や実行時エラーまでは確認できていない。読み取り専用の診断で見える範囲と、実際のブラウザ操作の間には差がある点は割り切っている。
