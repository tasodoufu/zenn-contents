回帰テストが緑でも、守りたい処理を実際には通っていないことがあります。

Go製OSSのglob処理を調べたところ、「`**`を含まないパターンは高コストな走査に入れない」ためのテストがありました。しかし、そのテスト入力はもっと手前のサイズ制限で拒否されており、対象の分岐を削除してもテストは成功したままでした。

この記事では、このような**通るだけの回帰テスト**を見つけ、壊れにくく直す方法を、実例を一般化しながら説明します。

## 背景：入力処理には複数の関門がある

対象の処理は、globパターンを正規化し、複雑すぎる入力を拒否してから、必要な場合だけセグメント列を構築します。簡略化すると次の形です。

```go
type compiledGlob struct {
    pattern  string
    segments []string
}

func compileGlob(pattern string) compiledGlob {
    g := compiledGlob{pattern: normalize(pattern)}

    if g.tooComplex() {
        return g
    }

    if hasGlobstarSegment(g.pattern) {
        g.segments = splitSegments(g.pattern)
    }
    return g
}
```

最後の分岐は、`**`を含まないパターンを不要なセグメント走査から外す性能上のゲートです。

ところが、元の回帰テストは約8KBのパターンを使っていました。実装の上限は1,024バイトまたは64セグメントなので、この入力は `hasGlobstarSegment` を調べる前に `tooComplex` で返されます。

処理の流れは、期待していた

```text
正規化 → サイズ検査を通過 → globstar判定 → 高コスト処理を回避
```

ではなく、実際には

```text
正規化 → サイズ超過で終了
```

でした。

## なぜ元のテストは誤検知したのか

元のテストには、入力が `**` を含まないことを確かめるアサーションがありました。

```go
require.False(t, hasGlobstarSegment(pattern))
```

この条件自体は正しいのですが、**その条件を実装が参照する地点まで入力が到達すること**は保証していません。

さらに、テストは1回あたりの割り当て量が閾値より小さいことを確認していました。大きすぎる入力は早期returnするため、対象ゲートを削除しても割り当て量は増えません。結果として、テスト名、コメント、アサーションはもっともらしいのに、回帰を検出できない状態になっていました。

ここで重要なのは、出力だけでなく**経路の前提条件**もテスト対象だということです。

## まずミューテーションで「赤になるか」を確認する

回帰テストを評価する最短の方法は、守るはずの処理を意図的に壊すことです。今回はglobstar判定を外し、すべての許可済みパターンでセグメント列を構築するよう変更しました。

```diff
- if hasGlobstarSegment(g.pattern) {
-     g.segments = splitSegments(g.pattern)
- }
+ g.segments = splitSegments(g.pattern)
```

この状態でも元のテストスイートは成功しました。つまり、そのテストは対象のゲートに対する回帰テストとして機能していません。

これは専用のミューテーションテストツールがなくても実施できます。

1. テストが守ると主張している分岐を特定する。
2. 一時ブランチやworktreeで、その分岐を削除または反転する。
3. 対象テストをキャッシュなしで実行する。
4. テストが失敗しなければ、入力経路とアサーションを見直す。
5. 本体の変更を戻し、修正後のテストでもう一度同じ変異を試す。

Goでは `-count=1` を付けると、結果キャッシュの影響を避けて対象テストを再実行できます。

```bash
go test -count=1 -run '^TestNonGlobstarDoesNotEnterWalk$' ./path/to/package
```

## 修正1：入力が対象経路へ到達できることを固定する

テスト入力を、上限内の約505バイト・64セグメントに縮めました。そのうえで、入力が拒否されていないことを明示的に検査します。

```go
pattern := strings.Repeat("segment/", 63) + "*"
compiled := compileGlob(pattern)

require.False(t, compiled.tooComplex(),
    "fixture must be admitted so the gate is exercised")
```

このアサーションは、一見すると実装の詳細に近く見えます。しかし今回のテスト目的は「許可された非globstar入力が、高コストな経路へ入らないこと」です。入力の許可はその契約の一部であり、暗黙の準備処理ではありません。

上限値が将来変わってフィクスチャが再び拒否されるようになっても、テストは別の理由で緑にならず、前提条件の崩壊を明示して失敗します。

## 修正2：性能の代理指標ではなく、守りたい不変条件を検査する

割り当て量の閾値は、ランタイムや入力サイズの影響を受けます。また、入力を上限内に縮めると、ゲートを削除した場合でも従来の緩い閾値を下回りました。

そこで、性能を生む構造そのものを検査します。

```go
assert.Nil(t, compiled.segments,
    "non-globstar pattern must not compile a segment walk")
```

このアサーションが表す不変条件は明確です。

- `**` を含まない。
- 入力制限を通過している。
- それでもセグメント走査用のデータは構築されない。

修正後に同じミューテーションを加えると、対象テストは `compiled.segments` が非nilになった地点で失敗しました。これで初めて、ゲートの削除を直接検出できる回帰テストになりました。

## ベンチマークと回帰テストの役割を分ける

同じコードにはベンチマークもありましたが、通常の `go test` ではベンチマークは実行されません。Goの公式ドキュメントでも、`BenchmarkXxx` は `-bench` を指定して実行する別の仕組みとして説明されています。

そのため、役割を次のように分けるのが安定します。

- **回帰テスト**: ゲートを削除すると必ず失敗する、決定的な不変条件を検査する。
- **ベンチマーク**: 許可済みの同じ入力を使い、変更前後の速度や割り当て量を観測する。

性能値そのものがAPI契約なら閾値テストが必要な場合もあります。しかし、今回のように「特定のデータ構造を作らないこと」が性能改善の直接原因なら、構造アサーションのほうがノイズに強く、失敗理由も明確です。

## 検証結果

修正後は次を確認しました。

```bash
go test -count=1 ./internal/mcp
go vet ./internal/mcp
git diff --check
```

対象パッケージのテスト、静的検査、差分検査は成功しました。また、Linux、macOS、Windowsビルドを含む公開CIも成功しています。

さらに一時worktreeでglobstarゲートを削除して対象テストを実行すると、修正後の構造アサーションが失敗しました。テストが緑になる確認だけでなく、**意図した欠陥を入れたとき赤になる確認**まで行っています。

## 回帰テストをレビューするときのチェックリスト

同種の問題は、入力検証、認証、キャッシュ、フォールバック、プラットフォーム分岐などでも起こります。レビューでは次を確認すると見つけやすくなります。

- フィクスチャは対象分岐より手前で拒否、スキップ、短絡されていないか。
- テスト名が主張する条件へ到達したことを、アサーションで固定しているか。
- 出力が同じになる別経路でもテストが通らないか。
- 時間やメモリの緩い閾値だけで、構造的な契約を代用していないか。
- 守る処理を削除・反転したとき、対象テストは確実に失敗するか。
- ベンチマークの入力も、現在の入力制限を通過しているか。
- テストコメント内の測定値は、現在も到達可能な経路のものか。

## 学び

回帰テストの価値は、成功することではなく、守るべき回帰が入ったときに失敗することです。

特に複数の早期returnがある処理では、テスト入力の性質だけを確認しても不十分です。入力が対象経路へ到達する前提を固定し、できるだけ守りたい不変条件を直接検査します。そして最後に小さなミューテーションを加え、テストが本当に赤になるかを確認します。

この3点だけでも、もっともらしく緑のまま残るテストをかなり減らせます。
