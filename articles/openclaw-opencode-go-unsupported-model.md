こんにちは、豆腐たそです。

この記事は、AIアシスタントの**メギ**と一緒に、OpenClawからOpenCode Goの新しいモデルを使おうとして遭遇した問題と、その切り分けをまとめた記録です。

結論から言うと、モデルIDを手動登録すればAPIへのリクエストは通りました。しかし、短い疎通確認が成功しても、通常の会話では空レスポンス判定や再試行が発生しました。未対応モデルを「呼び出せる」ことと「安定して使える」ことは別物でした。

## 環境

検証時の主な構成は次のとおりです。

- OpenClaw `2026.7.1-2`
- OpenCode Go
- OpenClaw GatewayをTailscale Serve経由で利用
- WebChatからモデルを切り替え

OpenClawが正式に認識していないモデルを指定すると、最初は次のようなエラーになりました。

```text
Unknown model: opencode-go/<model-id>
```

APIキーが間違っているようにも見えますが、今回は認証ではなく、OpenClaw側のモデルカタログに該当IDがないことが原因でした。

## モデルIDを登録すれば動くのか

そこで、元のファイルをバックアップしたうえで、OpenClawのOpenCode Go向けモデルカタログに対象モデルを追加しました。

追加後は、短い疎通確認で次の流れを確認できました。

1. OpenClawからOpenCode Goへリクエストを送信
2. APIがHTTP `200 OK`を返す
3. モデルが短い確認文字列を返す

ここだけを見ると成功です。しかし、通常の会話を続けると別の問題が起きました。

## 実際に起きた問題

Gatewayのログには、次のような状態が記録されていました。

```text
response ... status=200 contentType=text/event-stream
empty response detected
retrying 1/1 with visible-answer continuation
empty response retries exhausted
incomplete turn detected
```

重要なのは、APIがエラーを返したわけではない点です。HTTPレベルでは成功しているのに、OpenClawは受け取ったストリームから表示可能な回答を組み立てられず、空レスポンスとして扱っていました。

その結果、次の症状が見られました。

- 返答が表示されない
- OpenClawが回答生成を自動再試行する
- WebChatの再接続と重なり、操作が不安定に見える
- 同じ入力が二重に処理されたように見える場面がある

最後の二重処理については、モデルだけが原因と断定できません。ブラウザ側の再送、WebSocketの再接続、Gateway側のリカバリーなども候補になります。ただし、少なくとも同じ時間帯に空レスポンスと再試行が発生していました。

## なぜ短いテストだけ成功したのか

モデルカタログへの手動追加で解決できるのは、主に「そのモデルIDをOpenClawが受け付けるか」という入口の問題です。

一方、実運用では次の互換性も必要です。

- Server-Sent Eventsのチャンク形式
- 終了理由の表現
- reasoningと通常テキストの扱い
- ツール呼び出しの形式
- 空チャンクや終端イベントの解釈
- モデル固有のメタデータ

短い文章だけを返すテストでは表面化せず、長い応答やツール利用で初めて問題になることがあります。今回も「疎通成功」を「完全対応」と早合点してしまいました。

## 安全に試すための運用

未対応モデルへ挑戦する場合は、全面移行よりもカナリア運用が安全です。

1. 正式対応モデルを既定のまま維持する
2. 設定と変更対象ファイルをバックアップする
3. 未対応モデルは一時セッションで試す
4. 短文、長文、コード生成、ツール利用を別々に検証する
5. GatewayログでHTTP成功だけでなく、完了状態まで確認する
6. 問題が出たら既定モデルへ戻す

疎通確認では、少なくとも次の観点を分けて試すとよさそうです。

| テスト | 確認したいこと |
| --- | --- |
| 短い固定文字列 | 基本的な認証とルーティング |
| 数段落の文章 | ストリーミング応答の組み立て |
| コード生成 | 長い出力とMarkdownの処理 |
| ツール呼び出し | 関数呼び出し形式の互換性 |
| 連続した会話 | セッション履歴と再試行の挙動 |

## 今回の判断

いったん正式対応しているOpenAIモデルへ戻しました。OpenCode Goが全面的に不安定だと判断したわけではありません。今回確認できたのは、**このOpenClawバージョンと、手動登録した未対応モデルの組み合わせでは安定運用できなかった**ということです。

今後は既定モデルを安全網として残しながら、別セッションでOpenCode Goを検証します。正式対応版が公開されたら、同じテスト項目で再確認する予定です。

## おわりに

今回の一番の学びは、`200 OK`と「アプリケーションとして正常に使える」の間には大きな差があることでした。

低レイヤーの開発でも、パケットが届いたこととプロトコル全体が正しく動くことは別です。AIモデルの接続でも、認証、ルーティング、ストリーム処理、ツール呼び出しを層ごとに切り分ける姿勢が役立ちました。

失敗して終わりではなく、安全に戻せる状態を作ってからまた挑戦します。
